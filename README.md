# Quests

A [Logos Basecamp](https://github.com/logos-co/logos-basecamp) quest system in two
modules, built with [logos-module-builder](https://github.com/logos-co/logos-module-builder):

| Directory | Module | Type | Role |
|---|---|---|---|
| `core/` | `quests_core` | `core` (headless) | The quest system. Holds quest definitions and per-quest progress. Any module can start, advance and complete quests through its API and follow its events. Runs under Basecamp or `logosctl` alike. |
| `editor/` | `quest_editor_ui` | `ui_qml` + C++ backend | The quest editor: a GUI with its own backend that authors quests in `quests_core` and can run them through their lifecycle for testing. |

The split is the point: a Basecamp view is not addressable by other modules, so the
quest system itself is a headless core, and the editor is one client of it among
many (a game, Maps, ...). The editor backend is a thin Qt-typed proxy
(`modules().quests_core`) plus editor-only logic (draft validation, templates).

## Module API (`quests_core`)

```
// definitions (the editor's side)
bool        saveQuest(questId, questJson)     // JSON object; replaces if the id exists
bool        deleteQuest(questId)
std::string getQuest(questId)                 // "" if unknown
std::string listQuests()                      // [{"id", "quest", "progress"}]
int64_t     questCount()

// lifecycle (any module's side)
bool        startQuest(questId)               // available -> active
bool        completeObjective(questId, objectiveId)
bool        completeQuest(questId)            // active -> completed
bool        resetQuest(questId)               // -> available, objectives cleared
std::string getProgress(questId)              // {"state", "completedObjectives"}

events:     questSaved  questDeleted  questStarted  objectiveCompleted(questId, objectiveId)
            questCompleted  questReset
```

Quest definitions are opaque JSON so the editor owns the schema. Suggested keys:
`title`, `description`, `objectives: [{id, title}]`, `rewards`.

From another module, declare `"dependencies": ["quests_core"]` and call
`modules().quests_core.startQuest(...)` (typed client generated by the builder), or from
QML `logos.callModuleAsync("quests_core", "startQuest", [id], cb)`.

## Build

```bash
nix build ./core                                                  # result/: plugins/quests_core/...
nix build ./editor --override-input quests_core path:$PWD/core    # the editor, against the local core
nix build ./editor                                                # the editor, against the published core
```

Nix only sees git-tracked files: `git add` new sources and assets before building.

## Run in Basecamp (development)

```bash
cd editor
nix run . --override-input quests_core path:$PWD/../core          # opens the editor + core in Basecamp
nix run .#ui-dev --override-input quests_core path:$PWD/../core   # same, with QML hot reload
```

Inside [logos-workspace](https://github.com/logos-co/logos-workspace) the two modules are
the inputs `quests-core` and `quests-editor-ui`; the override is automatic there:

```bash
ws build --group own
nix run "$LOGOS_WORKSPACE_ROOT#quests-editor-ui--ui-dev" -- --user-dir /tmp/bc-quests
```

Headless, with `logosctl`: install `quests_core`'s `.lgx`, then
`logosctl call quests_core saveQuest str:demo 'json:{"title":"Demo"}'` and
`logosctl call quests_core startQuest str:demo`.

## Rules of the road

- Only `bool`, `int64_t`, `std::string` and std containers of them cross the module
  boundary; structured data travels as JSON text. Keep methods and `.rep` slots to
  at most 4 arguments.
- `metadata.json` descriptions: ASCII only, no semicolons (CMake splits on them).
- Render peer-supplied text with `textFormat: Text.PlainText`.
- `quests_core` keeps state in memory for now. Persist through `storage_module`
  before shipping.
